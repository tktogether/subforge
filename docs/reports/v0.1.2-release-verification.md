## 1. 验证范围

本次验证覆盖三类发布产物：

1. GHCR 上的容器镜像（默认镜像与最小镜像各一套标签）。
2. GitHub Release 上的预编译可执行文件。
3. 容器内的运行时行为（鉴权、订阅转换、HTTPS 上游抓取）。

交叉编译产物的哈希一致性、OpenWrt 打包验证见 `deploy/README.md` 与
[v0.1.0 质量核查报告](quality-audit.md)，本报告不重复。

## 2. 发布流水线的改动

v0.1.0 的公开镜像存在两个可用性缺陷：只有 `linux/amd64` 单一架构，且运行层是 `scratch`，
镜像内没有任何根证书，抓取 HTTPS 订阅源必然失败。v0.1.2 的流水线改动如下：

| 项目 | v0.1.0 | v0.1.2 |
| --- | --- | --- |
| `:latest` 使用的 Dockerfile | `Dockerfile`（`scratch` 运行层） | `Dockerfile.alpine`（`alpine` 运行层） |
| 镜像架构 | 仅 `linux/amd64` | `linux/amd64` + `linux/arm64` |
| 镜像自报版本 | `subforge dev (commit none, built unknown)` | `subforge v0.1.2 (commit f62f9d7d, built 2026-10-20T03:08:03Z)` |
| 镜像内根证书 | 无 | 291 个（`/etc/ssl/certs`） |
| 最小镜像标签 | 无独立标签 | `:<tag>-scratch` 与 `:latest-scratch` |

流水线改动位置：

- `.github/workflows/release.yml:79` `Compute build metadata` 步骤产出 `version`、`short`、
  `date` 三个 output，交叉编译与两个镜像构建共用同一套取值。
- `.github/workflows/release.yml:116` `Set up QEMU`（`docker/setup-qemu-action@v3`），
  用于在 amd64 运行器上构建 arm64 镜像。
- `.github/workflows/release.yml:126` 构建默认镜像，`:130 file: ./Dockerfile.alpine`，
  `platforms: linux/amd64,linux/arm64`，传三个 build-args。
- `.github/workflows/release.yml:140` 构建最小镜像，`:144 file: ./Dockerfile`，同样双架构，
  标签加 `-scratch` 后缀。
- `Dockerfile:25` 与 `Dockerfile.alpine:21` 使用
  `FROM --platform=$BUILDPLATFORM golang:1.26-bookworm AS builder`；
  `:28-29` / `:24-25` 声明 `ARG TARGETOS` 与 `ARG TARGETARCH`；
  `:54` / `:44` 用 `GOOS=${TARGETOS} GOARCH=${TARGETARCH}` 交叉编译。

## 3. GHCR 镜像验证结果

仓库 `ghcr.io/tktogether/subforge` 公开，**匿名即可拉取**。四个标签均返回 HTTP 200：
`v0.1.2`、`latest`、`v0.1.2-scratch`、`latest-scratch`。

`docker manifest inspect` 显示 `v0.1.2` 与 `latest` 的 index 中为 **2 个平台条目
（linux/amd64、linux/arm64）+ 2 个 attestation 条目**；`latest-scratch` 同为双架构。

解开镜像层后直接执行其中的二进制，实测结果：

| 镜像 | 运行层 | 自报版本 | `/etc/ssl/certs` 条目数 | amd64 各层压缩后合计 |
| --- | --- | --- | --- | --- |
| `ghcr.io/tktogether/subforge:v0.1.2`（等于 `:latest`） | `alpine:3.20` + `ca-certificates` + `tzdata` | `subforge v0.1.2 (commit f62f9d7d, built 2026-10-20T03:08:03Z)` | 291 | 20,046,583 B |
| `ghcr.io/tktogether/subforge:latest-scratch` | `scratch` | `subforge v0.1.2 (commit f62f9d7d, built 2026-10-20T03:08:03Z)` | 0 | 15,961,905 B |

`v0.1.2` 的 amd64 manifest 摘要为
`sha256:1450a293e6316f291da67d25d00ab83063e610bd1072eca34681ab5dd362aff5`。

### 3.1 容器运行时行为

以下用例在 `:v0.1.1` 上执行，其镜像结构与 `:v0.1.2` 同源：

- 带 `-token` 启动后，不带令牌访问 `/healthz` 返回 **401**，响应头为
  `Www-Authenticate: Bearer realm="subforge"`；带 `X-Token` 请求头返回
  `{"status":"ok"}` 与 HTTP 200。鉴权是全局的，`/version` 与 `/` 同样受保护。
- `/sub` 以 HTTPS 上游（`testdata/fixtures/mixed-subscription.txt`）为输入，
  返回 **HTTP 200、4871 字节**。
- 容器内直接执行 `convert` 抓取同一 URL：`完成: clash.meta, 4888 字节, 12 节点, 861ms`。
- arm64 镜像在装有 QEMU 的机器上可直接运行并正确自报版本，说明镜像内的二进制
  确为 arm64 且可执行。

## 5. 已知取舍与遗留

1. **最小镜像不含根证书，这是设计取舍。** `scratch` 运行层没有 `/etc/ssl/certs`，
   只适合 `http://` 上游或本地文件输入。需要抓取 HTTPS 订阅源时应使用默认镜像。
2. **旧标签保留。** `:v0.1.0` 与 `:v0.1.1` 仍可拉取，它们保留旧行为
   （`:v0.1.0` 为单架构、`scratch` 运行层；`:v0.1.1` 已双架构但仍以 `scratch` 为默认）。
   引用旧结论时必须写明标签。
3. **多架构镜像依赖 QEMU。** 流水线中的 `docker/setup-qemu-action` 是 arm64 镜像能在
   amd64 运行器上构建的前提；若移除该步骤，发布会在构建阶段失败。
4. **未验证项。** 未在真实 arm64 设备上做长时间运行测试；未在真实 OpenWrt 设备上执行
   `opkg install`。

## 6. 复现方式

```bash
# 拉取并查看镜像架构
docker pull ghcr.io/tktogether/subforge:latest
docker manifest inspect ghcr.io/tktogether/subforge:latest

# 运行默认镜像（注意监听地址，容器内默认为 127.0.0.1）
docker run --rm -p 25500:25500 ghcr.io/tktogether/subforge:latest \
  serve -listen 0.0.0.0:25500 -token <YOUR_TOKEN>

# 查看镜像自报版本
docker run --rm ghcr.io/tktogether/subforge:latest version
```
