# 核查与验证报告目录

本目录存放 SubForge 的质量核查报告与发布验证报告。报告由核查人独立产出，
记录当时的核查范围、实测数据、发现的问题与最终结论，用于回答两个问题：

1. 这个版本当时是否达到了验收标准？
2. 报告中的结论是在什么条件下、用什么方法测出来的？

报告是**历史记录**，不随实现变化而回填。如果后续版本修复了报告中的问题，
应在新报告中体现，而不是修改旧报告。

发布类报告（`vX.Y.Z-release-verification.md`）与里程碑报告的分工不同：里程碑报告回答
"这一版整体是否可交付"，发布报告只回答"这一次发布的产物是否可用、边界在哪"。
README 与 Wiki 中涉及具体数值的表述应链接到本目录，而不是把数值抄进正文
（见 [../style-guide.md](../style-guide.md) 第 9 节）。

## 二、核查维度说明

现有的 M1 报告按以下五个维度组织，后续报告建议沿用同一结构，便于横向对比。

| 维度 | 核查内容 | 常用手段 |
| --- | --- | --- |
| 功能完整性 | 全部目标格式的端到端转换、核心业务流程、边缘场景、负例处理 | 端到端转换脚本、目标格式全量遍历 |
| 性能达标率 | 关键路径的基准测试数值与内存分配 | `go test -bench`，与设计书预算对比 |
| 代码合规性 | 构建、静态检查、单元测试、许可证合规 | `go build`、`go vet`、`go test` |
| 稳定性 | 单元测试与集成测试通过率、兼容性测试、内存泄漏 | 全量测试、`-race`、长稳运行 |
| 安全与配置 | 鉴权、令牌、路径穿越、默认配置风险 | 代码审查与手工验证 |

## 三、新增报告的约定

1. **文件名**：使用小写连字符，包含里程碑或主题，例如 `quality-audit-m2.md`、
   `security-review-2026-11.md`。
2. **必备头部**：标题、日期、适用版本或里程碑、一句话结论。
3. **数据必须可复现**：给出测量命令与运行环境（操作系统、Go 版本、硬件规模），
   使读者可以自行复现同一组数值。
4. **区分事实与判断**：实测数值、命令输出属于事实；"是否达标"属于判断，
   必须写明所依据的阈值来自哪里（设计书预算、CI 门禁或团队约定）。
5. **未验证项要显式列出**：没有实际执行的检查项不得记为通过。
6. **完成后在本文件的清单表中登记一行。**

## 四、与其它文档的关系

- 与 [../compatibility.md](../compatibility.md) 的关系：兼容性差异表的条目通常来自
  核查过程中的金测（与参考实现逐字节或逐字段比对），差异表记录"差在哪"，
  核查报告记录"这一版整体是否可交付"。
- 与 [../design/](../design/) 的关系：核查报告中的性能阈值、验收标准引用设计书的预算，
  设计书是标准的来源，核查报告是达标情况的证据。
- 与仓库 [CONTRIBUTING.md](../../CONTRIBUTING.md) 的关系：CI 门禁的阈值定义在
  Makefile 与工作流中，核查报告可以引用门禁结果，但不应替代门禁本身。
