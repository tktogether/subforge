# v0.1.4 发布验证报告

- **日期**：2026-10-20
- **适用版本**：v0.1.4（提交 `a75fd784`）
- **结论**：镜像开箱即用。官方镜像预设了监听地址与数据目录，`docker run` 不加任何参数即可从宿主机访问控制台并使用订阅管理；默认镜像与最小镜像均为双架构、自带版本号、HTTPS 上游可正常抓取。

---

## 1. 验证范围

本次发布相对 v0.1.3 的改动集中在"容器开箱即用"，需要确认的是：

1. `serve` 的环境变量默认值是否真的生效，命令行参数与配置文件是否仍能覆盖它；
2. 官方镜像裸跑（不传任何参数）时，端口发布、控制台外壳、订阅管理接口是否都可用；
3. 镜像是否仍是双架构、是否仍能正确注入版本号；
4. 默认镜像（alpine 运行层）是否仍具备根证书，能否抓 HTTPS 上游；
5. 交叉编译产物与 Release 资产是否照常产出。

## 2. 被验证的改动

| 位置 | 改动 |
| --- | --- |
| `cmd/subforge/serve.go` | 四个启动选项接受环境变量作为默认值（`SUBFORGE_LISTEN`、`SUBFORGE_TOKEN`、`SUBFORGE_CONFIG`、`SUBFORGE_DATA_DIR`）；数据目录缺失时自动创建；未启用订阅管理时打印一行提示 |
| `Dockerfile`、`Dockerfile.alpine` | 新增 `ENV SUBFORGE_DATA_DIR=/data` 与 `ENV SUBFORGE_LISTEN=0.0.0.0:25500` |
| `docker-compose.yml` | 去掉覆盖 `command` 的写法，改为在 `environment` 中给出同样的两个变量 |
| `deploy/openwrt/files/subforge.init` | 修正为设置 `SUBFORGE_DATA_DIR`（原先设置的是已废弃的 `SUBFORGE_DATA`，并把 `SUBFORGE_CONFIG` 指向一个目录，会导致服务启动失败） |
| `.dockerignore` | 补充排除 `docs/`、`tools/`、`web/node_modules/`、`web/coverage*/`、`.tmp/`、`.zcode/`、`.compat/`、`.gocache/` |

优先级为**环境变量 < 命令行参数 < INI 配置文件同名项**（`cmd/subforge/serve.go:123`）。

| --- | --- | --- |
| 平台 | linux/amd64、linux/arm64 | linux/amd64、linux/arm64 |
| 自报版本 | `subforge v0.1.4 (commit a75fd784, built 2026-10-20T05:12:49Z)` | `subforge v0.1.4 (commit a75fd784, built 2026-10-20T05:12:49Z)` |

两个镜像的 manifest 除平台条目外还各带 2 个 attestation（`architecture`/`os` 为 `unknown`），这是 buildx 默认生成的来源证明，属正常现象。

### 4.1 裸跑行为（决定性检查）

```bash
docker run -d --name sf-rel -p 25500:25500 -v sf-rel-data:/data \
  ghcr.io/tktogether/subforge:v0.1.4
```

不传任何参数、不覆盖 `command`，容器 `Up`，端口映射为 `0.0.0.0:25500->25500/tcp`。从宿主机访问：

| 端点 | 状态码 | 说明 |
| --- | --- | --- |
| `/` | 200 | 控制台外壳 |
| `/healthz` | 200 | 健康检查 |
| `/api/version` | 200 | 运行时信息 |
| `/api/airports` | 200 | 正文 `{"airports":[]}`，说明订阅管理已启用 |
| `/api/targets` | 200 | 目标格式清单 |

容器内 `/data` 出现 `subforge.db`、`subforge.db-shm`、`subforge.db-wal` 三个文件；`docker exec sf-rel env` 显示 `SUBFORGE_DATA_DIR=/data` 与 `SUBFORGE_LISTEN=0.0.0.0:25500`；启动日志包含"订阅管理已启用: /data"与"subforge v0.1.4 监听 0.0.0.0:25500"。

### 4.2 容器内抓取 HTTPS 上游

在同一个容器里执行 `convert`，上游使用仓库内的公开测试夹具（HTTPS）：

```text
管线: 12 -> 12 节点
完成: clash.meta, 4871 字节, 12 节点, 781ms
```

即默认镜像的根证书齐备，HTTPS 订阅源可正常抓取。

## 5. 已知取舍与遗留

1. **`v0.1.3` 及更早的标签仍是旧行为**，容器内必须显式传 `-listen 0.0.0.0:25500 -data-dir /data`；GHCR 上的历史标签不会重建。
2. **`-scratch` 标签不含根证书**，只适合上游全部为 `http://` 或本地文件的场景。
3. **未在真实 OpenWrt 设备上验证** `opkg install` 与 procd 拉起，只验证了 init 脚本设置的环境变量能让进程正常启动。
4. **镜像只有 amd64 与 arm64**，`linux/arm` 与 `windows/amd64` 只出现在 Release 的裸可执行文件中。

## 6. 复现方式

```bash
# 查看镜像平台
docker manifest inspect ghcr.io/tktogether/subforge:v0.1.4

# 查看镜像自报版本
docker run --rm ghcr.io/tktogether/subforge:v0.1.4 version

# 裸跑并检查宿主机可达性
docker run -d --name sf-rel -p 25500:25500 -v sf-rel-data:/data \
  ghcr.io/tktogether/subforge:v0.1.4
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:25500/api/airports
docker exec sf-rel ls /data
docker logs sf-rel
```

验证环境：WSL2 Ubuntu 22.04，Docker 29.1.3（overlayfs 存储驱动），16 vCPU。
