# SubForge 统一最终选择组 - 项目简报

**日期**：2026-11-03
**作者**：橙先生 / SubForge
**状态**：Implemented（2026-11-03）
**范围**：订阅渲染期的分组归并（`/subscribe`），不改节点解析、管线、拉取与缓存。

## 1. 问题陈述

**Who**：同时使用多个机场、并把规则源叠加到同一份订阅的用户。

**What**：每个机场的分组树、每个规则源/模板的分组树都各自带一个「最终节点选择组」。这些组在产物里并列存在，切换出口要在多个组里分别操作；规则源的选择目标还可能落到别的机场的选择组上。

**Where**：订阅方案（Profile）同时启用多个机场分组层、并绑定规则源时。

**When**：每次编辑方案、切换节点、排障时都会遇到。

**Why**：最终选择组分散导致管理成本高，且容易误判当前实际出口；规则源与机场的目标名对不上时，现有逻辑会静默回退到「漏网之鱼」，实际落点与规则源作者的意图不一致。

**Current State**：渲染器只做「规则目标名校正」（同义/相似名/兜底），没有「最终选择组」概念；分组剪枝只删没有被规则引用的组，两个最终组因为被服务组引用而都会保留。

## 2. 现状与根因（测试环境实测）

测试环境 `192.168.8.251:25500` 的方案「默认」（id=1）当前产物：

| 指标 | 实测值 |
|---|---|
| 节点数 | 86（ikuuu + 守候网络，已带来源前缀） |
| 分组数 | 35 |
| 最终节点选择组 | 2 个：`🔰 选择节点`（ikuuu）、`Lite Connect`（守候网络） |
| 两个最终组的成员 | 各 87 个，内容完全相同：86 个节点 + `DIRECT` |
| 引用最终组的服务组 | 33 个（ikuuu 3 个、守候网络 30 个） |
| 规则数 | 10599（守候网络 9414 + Aethersailor 1184 + 1 条 MATCH） |
| 规则源 Aethersailor 的选择组 | `🚀 手动选择`，19 条规则指向 |
| Aethersailor 缺失目标 | 69 条；其中 1114 条 `🎯 全球直连` 已按同义词落 `DIRECT`，其余约 45 条回退到 `🐟 漏网之鱼` |
| 当前 MATCH | `MATCH,🐟 漏网之鱼` → `🔰 选择节点` |

分组的指向关系可以概括为：

```
规则(守候网络) ──> 守候服务组 ──> Lite Connect ──> 86 节点 + DIRECT
规则(ikuuu)   ──> ikuuu 服务组 ──> 🔰 选择节点 ──> 86 节点 + DIRECT
规则(Aethersailor, 🚀 手动选择) ──> 兜底 🐟 漏网之鱼 ──> 🔰 选择节点
```

根因：

1. 机场导入把上游 `proxy-groups` 原样落库，每个机场保留自己的最终选择组（`internal/subforge/import.go:196-229`）。
2. 分组库按名字全局去重，但不同机场的最终组名字不同，因此不会合并。
3. 规则源只导入规则、不导入分组树（`internal/subforge/rulesources.go:543-565` 还会丢弃 FINAL/MATCH），其选择目标只能靠名字相似度或兜底落到某个机场的组（`internal/render/ruletarget.go:42-131`）。
4. 渲染阶段没有「哪些组是最终选择组」的语义，两个最终组都被服务组引用，剪枝不会删除（`internal/render/prune.go:9-50`）。

## 3. 目标与非目标

### 目标

1. 每份订阅只保留一个「最终节点选择组」，名字由系统指定或用户自定义。
2. 所有来源（机场、模板、规则源）的选择目标与服务组引用都收敛到这一个组。
3. 服务分组（Netflix、ChatGPT、国内服务等）保留，成员与来源专属节点不被合并或丢失。
4. 默认关闭；开启后可预览、可解释、可回滚；关闭时产物与现状逐字节一致（除生成时间）。
5. 在测试环境完成前/后对照验证，且产物能被 mihomo 加载。

### 非目标

- 不合并同名或不同名的服务分组。
- 不改变节点解析、来源级管线、出网选择、失败策略、缓存。
- 不把统一组写入全局分组库（渲染期生成；可选复用用户自建的同名自定义组）。
- 不重做规则源 manifest 体系，不自动补建规则源缺失的服务分组。

## 4. 约束

### 技术

- 产物必须确定性：分组顺序、成员顺序、规则顺序稳定。
- mihomo 的 `rules` 目标、`proxy-groups` 成员都必须引用真实存在的出站；不能产出悬空名字。
- 统一组在渲染前生成，必须经过现有 `ResolveRuleTargets` 与 `PruneUnusedGroups`。
- 支持所有渲染目标；至少保证 clash.meta 回归，sing-box/mellow/lineform 不退化。

### 兼容与回滚

- 新增配置默认关闭；旧库迁移只加列，不重命名/删除现有分组。
- 关闭开关即恢复原产物；统一组是渲染期虚拟组，不落库，可逆性高。
- 规则源 FINAL/MATCH 目前本来就被忽略；统一后由全局 MATCH 接管，不新增静默丢弃。

### 资源

- 纯内存变换，O(分组数 + 规则数)；预览会在服务端读一次规则源当前产物。
- 不新增外部依赖、不新增网络请求。

## 5. 方案对比

### 方案 A：渲染期收敛（推荐）

在引擎拿到最终节点列表、展开分组之后，识别每个来源的最终选择组，生成/复用一个统一组，改写分组引用与规则目标，最后交给现有目标校正与剪枝。

- 优点：不动源数据；按方案生效；可预览、可回滚；与现有剪枝/校正链路天然衔接；测试环境可直接验证。
- 缺点：需要新增识别算法与配置；规则源没有分组树时只能靠目标名/兜底目标识别，需要人工覆盖入口。
- 风险：识别误判；可通过证据预览、阈值、覆盖项和默认关闭控制。

### 方案 B：导入期规范化

导入机场分组时把每个机场的最终组重命名/合并为一个固定组，规则源导入时同步改写选择目标。

- 优点：DB 里就只有一套组，后续渲染简单。
- 缺点：破坏性、需要重新导入；不同方案无法使用不同统一组；规则源产物仍是只读文件，仍要改渲染；回滚困难；容易丢机场专属选择逻辑。
- 结论：不作为主方案，可在未来做一次性清理工具。

### 方案 C：只生成标准组骨架

忽略机场/模板自带分组，只生成「节点选择/自动选择/直连/拒绝/漏网」等标准组，规则按语义映射。

- 优点：产物最干净、最可预测。
- 缺点：丢掉机场自带的服务分组（Netflix、ChatGPT、国内服务等），行为变化过大；不满足「保留服务组」的隐含需求。
- 结论：不采用。

### 方案 D：只做手工映射

用户在方案里逐个来源指定「哪个组是最终组」，再指定一个统一组名。

- 优点：完全可控、无误判。
- 缺点：正是用户想避免的管理负担；每加一个机场/规则源都要维护。
- 结论：作为方案 A 的覆盖项（override），不作为唯一入口。

### 方案 E：只把 MATCH 指到一个新组

生成统一组，但只改 MATCH，不改服务组对各自最终组的引用。

- 优点：改动最小。
- 缺点：客户端里仍有多个最终选择组，服务组仍指向各自机场的最终组，问题未解决。
- 结论：不采用。

### 对比矩阵

| 维度 | A 渲染期收敛 | B 导入期规范化 | C 标准骨架 | D 手工映射 | E 只改 MATCH |
|---|---|---|---|---|---|
| 技术契合 | 🟢 高 | 🟡 中 | 🟡 中 | 🟢 高 | 🟢 高 |
| 保留服务组 | 🟢 是 | 🟡 部分 | 🔴 否 | 🟢 是 | 🟢 是 |
| 管理成本 | 🟢 低（自动+覆盖） | 🟡 中（需重导） | 🟢 低 | 🔴 高 | 🟢 低 |
| 可回滚 | 🟢 开关即回滚 | 🔴 难 | 🟢 开关 | 🟢 开关 | 🟢 开关 |
| 解决问题程度 | 🟢 完整 | 🟢 完整 | 🟡 部分 | 🟢 完整 | 🔴 不足 |
| 实施风险 | 🟡 中 | 🔴 高 | 🟡 中 | 🟢 低 | 🟢 低 |

## 6. 决策

**采用方案 A（渲染期收敛），并把方案 D 的手工指定作为覆盖项。**

关键决策：

1. **按方案（Profile）生效，不按全局**：不同订阅可以有不同的统一组名与来源组合；方案已经是层、规则源、机场范围的归属单位。
2. **默认关闭**：避免影响现有订阅；在测试环境先开启验证。
3. **统一组在渲染期生成，不落库**：不污染全局分组库；可选复用用户在同名自定义层建好的组，便于手工管理成员。
4. **统一组名**：`auto` 模式由系统使用标准名 `🚀 节点选择`（若已存在且可复用则复用，否则生成）；`custom` 模式用用户输入的名字。
5. **识别始终自动，覆盖可选**：默认自动识别每个来源的最终组；预览里可逐来源覆盖或忽略。
6. **全局 MATCH 指向统一组**：这样规则源缺失目标与选择目标都会落到统一组，而不是某个机场的兜底组；统一组本身包含 `DIRECT`，直连仍可选择。
7. **服务组保留**：只改写它们对最终组的引用，不改成员中的节点；不合并服务组。

## 7. 详细设计

### 7.1 概念

- **来源最终组（Terminal Group）**：某个来源（机场分组树、模板分组树、自定义分组层）里，被同来源其他分组大量引用、且主要用于「选择节点」的分组。例：ikuuu 的 `🔰 选择节点`、守候网络的 `Lite Connect`、Aethersailor 模板的 `🚀 手动选择`。
- **统一组（Unified Final Group）**：渲染期生成或复用的单一选择组，例如 `🚀 节点选择`。
- **规则源选择目标**：规则源产物里指向其自身选择组的规则目标（Aethersailor 的 `🚀 手动选择`，19 条）。规则源没有分组树，因此不能靠成员关系识别，只能靠目标名、兜底目标与人工覆盖。

### 7.2 配置模型

在 `profiles` 表新增一列（JSON 文本，空串 = 关闭）：

```json
{
  "enabled": true,
  "mode": "auto",
  "name": "🚀 节点选择",
  "include_direct": true,
  "keep_source_terminals": false,
  "overrides": {
    "group:airport:ikuuu": ["🔰 选择节点"],
    "group:airport:守候网络": ["Lite Connect"],
    "rule:Aethersailor": ["🚀 手动选择"]
  }
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `enabled` | 总开关；关闭时零行为变化 |
| `mode` | `auto`：系统使用标准名；`custom`：使用 `name` |
| `name` | 自定义统一组名；`mode=auto` 时可省略 |
| `include_direct` | 统一组是否包含 `DIRECT`，默认 true |
| `keep_source_terminals` | 是否把来源最终组保留为统一组的子选项，默认 false |
| `overrides` | 按来源覆盖识别结果；`group:` 前缀对应分组的 `source`，`rule:` 前缀对应规则源名 |

校验：

- `custom` 模式 `name` 必填；去首尾空白；禁止逗号、换行、`DIRECT`/`REJECT` 等内置出站名；长度上限 100。
- 若 `name` 已被一个非最终组、非自定义层的分组占用，返回 400/409 并说明冲突，不静默改。
- 若 `name` 命中某个来源最终组，或命中自定义层分组（source 为空），则复用该组，不新建。
- `overrides` 里的来源不存在时给 warning，不阻断。

### 7.3 识别算法

输入：展开后的分组（含 `Source` 元数据）、最终节点名、最终规则、规则源元数据。

1. **分组图**：按 `Group.Source` 分组（空 source 视为 `custom`；模板组标记为 `template`），统计每个组被同来源其他组作为成员引用的次数（入度）。
2. **候选条件**（满足任一）：
   - 入度 ≥ max(2, 同来源组数 × 20%)；
   - 名字命中选择语义关键词：`选择`、`手动`、`节点`、`代理`、`出口`、`proxy`、`select`、`manual`、`auto`、`connect` 等（归一化后匹配）；
   - 同来源规则中指向该组的目标占比 ≥ 20%（目标名在该来源分组里唯一时可用）。
3. **候选过滤**：必须是 `select`/`url-test`/`fallback`/`load-balance`；必须有节点成员或 `include_all_sources`/`include_self`/`use`；排除 `DIRECT`/`REJECT`/直连/拦截等内置语义。
4. **打分**：入度比例 × 3 + 名字命中 × 2 + 规则占比 × 2 + 覆盖全部节点 × 1；同分取分组顺序更靠前者，并给出 warning。
5. **每个来源最多一个最终组**；识别不到则不处理该来源，并在预览里标「未识别」。
6. **规则源**：从每个规则源的产物里收集：
   - 被丢弃的 FINAL/MATCH 目标（当前 `RuleSourceRules` 只统计条数，需要新增元数据返回）；
   - 规则目标计数；名字命中选择语义且不存在的目标，作为「选择目标别名」；
   - 显式覆盖项优先。
7. **模板**：模板分组树与机场分组树用同一套图算法；模板规则目标可作为辅助证据。

测试环境预期识别：

| 来源 | 识别结果 | 证据 |
|---|---|---|
| `airport:ikuuu` | `🔰 选择节点` | 入度 9/10；名字含「选择节点」；成员覆盖全部节点 |
| `airport:守候网络` | `Lite Connect` | 入度 31/31；成员覆盖全部节点 |
| `rule:Aethersailor` | `🚀 手动选择` | 19 条规则指向；规则源无分组树，按名字语义识别，可在预览覆盖 |

### 7.4 改写算法

在 `Engine.Run` 完成 `expandGroupExtras` 与 `ResolveGroups` 之后、构造 `render.Request` 之前执行：

1. **解析统一组名**：
   - `custom`：用 `name`；
   - `auto`：用 `🚀 节点选择`；
   - 若同名组是某个来源最终组，或自定义层分组：复用它（保留类型与成员，必要时补齐 `use`）；否则生成新组。
2. **构造统一组**：
   - 类型 `select`；
   - 成员 = 最终节点名（按当前顺序去重）+ 各最终组 `use` 的 provider 名 + `DIRECT`（`include_direct=true` 时）；
   - 放在 `proxy-groups` 第一位；
   - 不复用被识别最终组的 `IncludeAllSources` 等标志（此时已展开为真实名字）。
3. **改写分组成员**：
   - 所有分组（除统一组自身）成员中，凡等于任一来源最终组名的，替换为统一组名；
   - 去重、去掉自引用；空成员补 `DIRECT`（防止 mihomo 拒绝空组）。
4. **改写规则**：
   - 目标等于任一来源最终组名，或等于规则源选择目标别名：改为统一组；
   - 折叠 FINAL/MATCH 为一条，目标统一组，并移到规则末尾；
   - 没有 MATCH 时追加 `MATCH,<统一组>`；
   - 其余缺失目标交给现有 `ResolveRuleTargets`：先同义/相似名映射，再落到 MATCH 目标（此时就是统一组）。
5. **删除/保留来源最终组**：
   - 默认不保留；改写后它们不再被引用，现有 `PruneUnusedGroups` 会删除；
   - `keep_source_terminals=true` 时把它们作为统一组的子选项保留（P1 可选）。
6. **输出报告**：识别到的来源最终组、规则源目标、改写数量、回退数量、被删除的分组、统一组成员数。

订阅响应里不需要新增大量 header；统一过程中的 warning 进入服务日志，预览页完整展示。

### 7.7 边界情况

- **禁用/缺少配置**：直接跳过，产物与现状一致。
- **没有识别到任何来源最终组**：仍生成统一组并把 MATCH 指向它（`custom`/`auto` 的明确请求），但 warning 说明未识别；服务组引用不变。
- **同名冲突**：统一组名被非最终组占用 → 保存/预览时报错，不静默覆盖。
- **非 select 最终组**：若复用组是 `url-test`/`fallback`，保留其类型；若生成新组，默认 `select`。预览标注。
- **provider-only 来源**：统一组带上最终组的 `use` 列表，避免只靠节点名丢 provider 节点。
- **自建节点**：`nodes.Names()` 已包含方案选中的自建节点，统一组自动包含。
- **include/exclude**：在引擎之前已生效，统一组只使用最终节点集。
- **逻辑规则**：AND/OR/NOT/SUB-RULE 的目标字段用现有 `ruleTargetIndex` 口径，不误改参数里的逗号。
- **多个 MATCH**：折叠为一条并放末尾；避免旧规则里的 MATCH 提前截断。
- **规则源 FINAL 为 DIRECT/REJECT**：不映射为选择组；全局 MATCH 仍指向统一组，预览明确提示。
- **分组名/节点名同名**：以分组为准并 warning；避免把节点名当组改写。

## 9. 压力测试与风险预案

### Red Team

| 质疑 | 回应 |
|---|---|
| 自动识别会不会把服务组当最终组？ | 入度 + 名字 + 节点覆盖 + 规则占比四重证据；预览逐来源展示；可覆盖/忽略；默认关闭。 |
| 规则源没有分组树，`Lite Connect` 这类自定义名识别不了？ | 机场/模板有分组树可走图算法；规则源只能靠目标名/兜底目标/人工覆盖，预览会标「低置信」。 |
| 统一组包含所有节点，会不会改变来源原本的节点子集？ | 统一组的目标就是全局出口；服务组保留自己的子集；预览显示统一组与各最终组的节点数差异。 |
| 删掉来源最终组会不会让某些规则悬空？ | 所有指向它们的规则和成员引用在删除前已改写；最后仍走现有目标校正与剪枝。 |
| 关闭开关能否完全恢复？ | 是，纯渲染期变换；配置不落源数据；基线逐字节对比。 |

### Premortem

最可能的失败模式是「识别错了一个服务组」或「规则源自定义选择组没有被识别」。预案：

- 预览必须显示每个来源的证据与置信度；
- 低置信来源默认不自动改写，提示用户手工指定；
- 所有改写都有日志与计数；
- 保留 `overrides` 和 `keep_source_terminals` 两个逃生口；
- 测试环境先验证，再考虑给新方案默认开启。
